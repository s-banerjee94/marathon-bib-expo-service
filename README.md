# Marathon Bib Expo Service

The backend for running a marathon's bib expo: the days before a race when runners come to a venue to
pick up their bib and race goodies (T-shirt, medal, bottle...). Organizers import the participant list,
volunteers at the counter scan a bib and hand things over, and the organizers watch it all live on a
dashboard. Several organizations share one installation, each with its own events, staff and data.

## What it does

| Area | In short |
|---|---|
| **Events** | Organizations, events, races and age/gender categories, with per-plan limits |
| **Participants** | CSV import (Spring Batch, with per-row errors), search, export, and a signed QR link each runner can open to see their own status |
| **Expo counter** | Collect a bib with its goodies, one at a time or in bulk, undo, pending lists, and a searchable log of who handed what to whom |
| **Inventory** | Items with variants (sizes, colours), locations and a stock ledger. Link an event's goodies to stock and every hand-over takes a unit off the shelf; a shortfall report compares what is still owed against what is on hand |
| **Messaging** | SMS and WhatsApp campaigns and templates through configurable providers, plus a targeted re-send to named bibs |
| **Billing** | Usage-based invoices with GST PDFs, generated by an AWS Lambda |
| **Insight** | Event, organization and platform dashboards, an audit log, and in-app notifications |
| **AI assistant** | An MCP server inside the app, driven by a separate Python agent (`ai-agent/`) that acts with the user's own permissions |

Roles: `ROOT` and `ADMIN` run the platform, `ORGANIZER_ADMIN` and `ORGANIZER_USER` run an organization,
and a `DISTRIBUTOR` works the counter of one event.

## Tech stack

Java 17 · Spring Boot 4 (Web MVC, Security, Data JPA, Batch, Cache) · MySQL 8 · DynamoDB · S3 ·
AWS Lambda + EventBridge Scheduler · RS256 JWT · Spring AI (MCP server) · Caffeine · SpringDoc OpenAPI ·
Micrometer, Prometheus and Grafana. Locally, every AWS service runs in
[LocalStack](https://www.localstack.cloud/).

## Getting started

You need **Java 17+**, **Docker** and **OpenSSL**. Maven comes with the repo (`./mvnw`).

### 1. Create the JWT signing keys

Tokens are signed with an RSA key pair that is not committed. Create a development pair once:

```bash
mkdir -p keys
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out keys/jwt-private-dev.pem
openssl rsa -in keys/jwt-private-dev.pem -pubout -out keys/jwt-public-dev.pem
```

### 2. Start the infrastructure

```bash
docker compose up -d
```

| Service | Port | Purpose |
|---|---|---|
| MySQL 8 | 3306 | Organizations, users, events, inventory, billing |
| LocalStack | 4566 | DynamoDB, S3, Lambda and Scheduler |
| Prometheus | 9090 | Scrapes the app's metrics |
| Grafana | 3000 | Dashboards (`admin` / `admin`) |

On startup LocalStack runs `scripts/localstack-init.sh`, which creates every DynamoDB table and the S3
bucket. The MySQL schema is created by Hibernate the first time the app starts.

### 3. Point the app at your infrastructure

The app reads its settings from environment variables, with defaults in
`src/main/resources/application.yaml`. Those defaults expect the Docker stack on the maintainer's LAN
host, so when Docker runs on your own machine, set these:

```bash
export DB_HOST=localhost
export AWS_DYNAMODB_ENDPOINT=http://localhost:4566
export AWS_S3_ENDPOINT=http://localhost:4566
export AWS_LAMBDA_ENDPOINT=http://localhost:4566
export AWS_SCHEDULER_ENDPOINT=http://localhost:4566
```

`.env.example` lists the other settings. Docker Compose reads `.env` on its own, but the app does not:
either export the variables in your shell (`set -a; . ./.env; set +a`) or add them to your IDE's run
configuration.

### 4. Run it

```bash
./mvnw spring-boot:run
```

The app starts on **http://localhost:8080**. There is no hot reload, so restart after a code change.

- Swagger UI: http://localhost:8080/swagger-ui.html
- Health: http://localhost:8080/actuator/health

### 5. First steps

1. A `ROOT` user is created on first start, `root` / `root` by default (`ROOT_USERNAME`, `ROOT_PASSWORD`).
2. Log in with `POST /api/auth/login`, then click **Authorize** in Swagger UI and paste the access token.
3. Create an organization, then its users, then an event.
4. Import participants from a CSV and publish the event, and the counter endpoints come alive.

Outbound SMS and WhatsApp are stubbed locally (`MESSAGING_STUB_ENABLED=true`): they are logged, never
sent. Automatic billing is off too (`BILLING_SCHEDULING_ENABLED=false`), because LocalStack never fires
schedules.

### Optional: the AI agent

The assistant is a separate Python 3.13 service in `ai-agent/` and needs this app running.

```bash
cd ai-agent
cp .env.example .env    # model key, AWS and the MCP endpoint
uv sync
uv run uvicorn app.main:app --reload
```

It serves everything under `/ai`. A reverse proxy in front of it must pass `/ai/` through unchanged.

## How the code is organised

One Maven module and one jar, split into modules by package. Every direct sub-package of
`com.timekeeper.bibexpo` is a module, and a module may only call modules in a lower layer:

| Layer | Modules |
|---|---|
| 0 | `shared`: errors, security primitives, AWS and persistence config, utilities |
| 1 | `audit`, `notification`, `storage`, `demo` |
| 2 | `organization` |
| 3 | `event` (with `limit`, `stats`, `race`, `race/category`) |
| 4 | `user`, `participant`, `billing` |
| 5 | `identity`, `importer`, `messaging`, `participantaccess`, `reporting`, `inventory` |
| 6 | `distribution`, `invitation`, `passwordreset` |
| 7 | `ai`, `bootstrap` |

Modules call each other only through a published `api/` port or a `service/` interface; reading another
module's entities, DTOs and enums is allowed. `ModuleBoundaryRulesTest` (ArchUnit) fails the build when a
module breaks these rules.

Where data lives:
- **MySQL:** anything relational (organizations, users, events, races, categories, inventory, import
  jobs, invoices, messaging setup).
- **DynamoDB:** the high-volume expo data (participants, distribution logs, event counters,
  notifications, audit log, short links).
- **S3:** logos, profile pictures, AI attachments and invoice PDFs.

Other folders:
- `ai-agent/`: the Python assistant.
- `lambda/`: the billing Lambdas.
- `scripts/`: LocalStack setup.
- `grafana/` and `prometheus.yml`: monitoring.

## API at a glance

Swagger UI has every endpoint with its roles, request and response. The main groups:

| Area | Base path |
|---|---|
| Auth | `/api/auth` (login, refresh, logout, password reset, invitations) |
| Organizations and users | `/api/organizations`, `/api/users` |
| Events | `/api/events`, with `/races`, `/goodies`, `/limits`, `/dashboard`, `/billing` under an event |
| Participants | `/api/events/{eventId}/participants` (CRUD, lookup, export, `/batch-import`) |
| Counter | `/api/events/{eventId}/distribution` (collect, goodies, bulk, pending, logs) |
| Inventory | `/api/organizations/{organizationId}/inventory` (items, locations, stock, receipts, transfers, adjustments, event goodie links and shortfall) |
| Messaging | `/api/events/{eventId}/sms-campaigns`, `/whatsapp-campaigns`, templates, `/participant-messages` |
| Dashboards and billing | `/api/dashboard/organization`, `/api/dashboard/platform`, `/api/billing` |
| Other | `/api/audit-logs`, `/api/notifications`, `/api/public/**` (no login), `/sse` + `/mcp/message` (MCP) |

Authentication is a 15-minute access token sent as `Authorization: Bearer <token>`, and a 7-day refresh
token kept in an httpOnly cookie and rotated by `POST /api/auth/refresh`.

## Configuration

Every setting has a default in `application.yaml`. The ones you are most likely to change:

| Variable | Default | What it is |
|---|---|---|
| `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD` | LAN host, `3306`, `marathon_bib_expo`, `root`, `root` | MySQL |
| `AWS_*_ENDPOINT` | LAN LocalStack | Leave empty in production to use real AWS |
| `AWS_DYNAMODB_TABLE_PREFIX` | empty | Prefix for every DynamoDB table, e.g. `staging-` |
| `ROOT_USERNAME`, `ROOT_PASSWORD` | `root`, `root` | The first user |
| `JWT_PRIVATE_KEY_LOCATION`, `JWT_PUBLIC_KEY_LOCATION` | `file:keys/jwt-*-dev.pem` | The signing keys from step 1 |
| `JWT_COOKIE_SECURE` | `false` | Must be `true` in production (HTTPS) |
| `CORS_ALLOWED_ORIGINS` | `*` | Your frontend's exact origin in production |
| `MESSAGING_STUB_ENABLED` | `true` | `false` to really send SMS and WhatsApp |
| `SYSTEM_MESSAGING_SECRET_KEY`, `PARTICIPANT_ACCESS_QR_SECRET` | dev values | Replace in production |
| `DDL_AUTO` | `update` | Production runs `validate`, so schema changes there are applied by hand |

The `prod` profile (`application-prod.yaml`) holds the production overrides and gives its secrets no
defaults, so a missing one stops the app at startup.

## Tests

```bash
./mvnw test                                    # everything
./mvnw test -Dtest=ModuleBoundaryRulesTest     # module rules only, no infrastructure needed
```

`MarathonBibExpoApplicationTests` boots the whole app, so it needs MySQL and LocalStack running. Beyond
these two, changes are checked by exercising a running instance end to end rather than by unit tests.
